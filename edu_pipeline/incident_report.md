# Разбор дефектов модуля отчётности (Этап 7)

Исходный модуль: `data/final/buggy_report.py` (не изменён, работаем по циклу
**воспроизведение -> исправление -> регрессионный тест**).
Исправленная версия: `fixed_report.py`. Регрессионные тесты: `test_report.py`
(все зелёные - см. `results/tests_green_log.txt`).

По данным автора модуля, «на части данных возникают странные ошибки».
Ниже каждый дефект: как проявился, чем воспроизведён, в чём причина,
как исправлен и каким тестом защищён.

## Дефект 1. Падение на пустых данных

- **Симптом.** На пустой базе (или пустом файле заявок) отчёт падает с
  `ZeroDivisionError: division by zero` - вместо отчёта объяснений нет.
- **Воспроизведение.** `average_duration([])` ->
  `ZeroDivisionError - division by zero`.
- **Причина.** `return total / len(rows)` при `rows == []` - деление на ноль.
- **Исправление.** Пустой список проверяется явно и поднимается
  `ValueError("no data: rows is empty")` - понятная причина вместо «странной»
  ошибки. Заодно сумма переписана через `sum(...)`.
- **Регрессионный тест.** `test_report.py::TestAverageDuration::test_empty_rows_raises`
  (+ `test_normal_rows` на корректных данных).

## Дефект 2. Топ курсов возвращает худшие курсы

- **Симптом.** «Топ-2 курса» по заявкам выдавал самые непопулярные курсы -
  на данных из базы список шёл «снизу вверх».
- **Воспроизведение.** Данные: PY-100 x3, DA-200 x2, QA-150 x1;
  `top_courses(rows, limit=2)` -> `[('QA-150', 1), ('DA-200', 2)]`
  (ожидали `[('PY-100', 3), ('DA-200', 2)]`).
- **Причина.** `sorted(counts.items(), key=lambda kv: kv[1])` - сортировка
  по возрастанию; [:limit] берёт начало списка, то есть наименьшие счётчики.
- **Исправление.** Добавлен `reverse=True` - сортировка по убыванию.
- **Регрессионный тест.** `test_report.py::TestTopCourses::test_returns_most_popular`
  (+ `test_limit`).

## Дефект 3. find_by_status молча меняет список вызывающего

- **Симптом.** После вызова `find_by_status` у вызывающего «сами»
  перестраивались строки списка - данные менялись без видимой причины.
- **Воспроизведение.** Вход: `[('EDU-1', 'new', 24), ('EDU-2', 'enrolled', 36)]`;
  после `find_by_status(rows, 'new')` вход стал
  `[('EDU-2', 'enrolled', 36), ('EDU-1', 'new', 24)]` - `мутирует вход: True`.
- **Причина.** Внутри функции `rows.sort(key=lambda r: r[1])` - сортировка
  **на месте** меняет переданный список, причём эта сортировка для фильтрации
  вообще не нужна.
- **Исправление.** Сортировка удалена; фильтрация переписана через
  list comprehension по новому списку. Вход не мутируется.
- **Регрессионный тест.** `test_report.py::TestFindByStatus::test_does_not_mutate_input`
  (+ `test_filters_by_status`).

## Дефект 4. Падение на нестроковом номере заявки

- **Симптом.** Если номер заявки пришёл из внешнего файла числом, строка
  отчёта не собирается.
- **Воспроизведение.** `report_line(123, 'new')` ->
  `TypeError: can only concatenate str (not "int") to str`.
- **Причина.** Склейка строк оператором `+`: `"Заявка " + enrollment_id + ...`
  требует, чтобы все части были строками.
- **Исправление.** f-string: `f"Заявка {enrollment_id} в статусе {status}"` -
  любой тип приводится к тексту сам.
- **Регрессионный тест.** `test_report.py::TestReportLine::test_non_string_id`
  (+ `test_string_id`).

## Дефект 5. Соединение с базой не закрывается (попутный)

- **Симптом.** `load_enrollments` открывает соединение и никогда его не
  закрывает - файл базы остаётся занятым до сборщика мусора.
- **Причина.** Нет `conn.close()`.
- **Исправление.** Чтение обёрнуто в `try/finally` с `conn.close()`.
- **Регрессионный тест.** Покрывается остальными тестами модуля (функция
  переиспользуется); прямой проверки «соединение закрыто» не требуется -
  фиксируется здесь как попутное исправление.
