# Пояснение к схеме базы данных edu.db (Этап 4)

## Три таблицы

- **students** - справочник студентов. Ключ `student_email` - у почты естественная уникальность, и все заявки ссылаются на студента именно по ней.
- **courses** - справочник курсов. Ключ `course_code` (PY-100, DA-200...) - так курс обозначен и в заявках, и в прайсе.
- **enrollments** - заявки. Ключ `enrollment_id` (номер заявки EDU-ГГГГММ-NNNN). Два внешних ключа: `student_email` -> students, `course_code` -> courses.

## Почему так

1. **Справочники отдельно от заявок.** ФИО студента и название курса хранятся один раз, а не в каждой заявке: если в заявке опечатка в почте, её видно сразу - ссылка не найдёт студента.
2. **Внешние ключи + `PRAGMA foreign_keys = ON`.** Без этой настройки SQLite по умолчанию FK не проверяет; с ней попытка вставить заявку несуществующего студента падает с `IntegrityError` - именно это используется в `batch_load.py` для демонстрации rollback.
3. **Даты - TEXT в формате ГГГГ-ММ-ДД.** Такой формат сортируется лексикографически, то есть `ORDER BY created_date` работает правильно без преобразований.
4. **`duration_hours` REAL, `price_rub` INTEGER.** Длительность может быть дробной (2.5 часа), цена курса - целые рубли.
5. **Дубликаты закрывает PRIMARY KEY.** Повторная вставка заявки с тем же номером не создаёт вторую строку при `INSERT OR IGNORE` - это и есть защита ETL от дублей при повторном запуске.

## Связь с этапами

Схему создаёт `create_db.py` (функции `connect`, `ensure_schema`, `load_reference_data` - их переиспользуют `batch_load.py`, `queries.py`, `etl_import.py`, `export_data.py`). Справочники загружаются при создании базы, заявки попадают в неё через ETL (Этап 5). Все запросы - в `queries.py`, все параметризованы (`?`), пользовательские значения в текст SQL не подставляются.
