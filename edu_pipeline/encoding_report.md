# Отчёт по диагностике кодировок (Этап 7)

## Что было на входе

- `data/final/names_cp1251.txt` - список имён в кодировке CP1251 (Windows-1251);
- `data/final/names_utf8.txt` - тот же список в UTF-8, эталон для сравнения.

Открытие «в лоб» без указания кодировки не работает: Python по умолчанию
ожидает UTF-8, и CP1251-файл падает с `UnicodeDecodeError`.

## Что показала диагностика

Полная таблица попыток - `results/diagnostic_table.csv`, скрипт -
`unicode_diagnostics.py`. Ключевые факты:

| Файл | Кодировка | Результат |
| --- | --- | --- |
| names_cp1251.txt | utf-8 | `UnicodeDecodeError: invalid continuation byte (байт 0xc8)` |
| names_cp1251.txt | **cp1251** | OK, текст совпал с эталоном |
| names_utf8.txt | **utf-8-sig** | OK - эталон (файл начинается с BOM) |
| names_utf8.txt | utf-8 | OK, но в тексте остался символ BOM - совпадения с эталоном нет |
| names_utf8.txt | cp1251 | `UnicodeDecodeError: character maps to <undefined> (байт 0x98)` |

## Как отличали «правильную» кодировку

Просто «декодировалось без ошибки» - недостаточный признак: файл можно
разобрать в неверной кодировке и получить нечитаемый текст. Поэтому итоговая
проверка - сравнение с эталоном: текст считается прочитанным верно, только
если он побайтно совпал с содержимым `names_utf8.txt`, прочитанным как
`utf-8-sig`.

## Почему BOM важен

Файл `names_utf8.txt` начинается с трёх байт `EF BB BF` - это BOM, метка
UTF-8. При чтении как `utf-8` метка попадает в текст первым символом
(`\ufeff`) и сравнение с эталоном проваливается. Правильное чтение -
`utf-8-sig`, который снимает метку автоматически. Кстати, все CSV проекта
тоже читаются с `utf-8-sig` по этой же причине.

## Вывод и правило проекта

- `names_cp1251.txt` читать в кодировке `cp1251`;
- `names_utf8.txt` (и все CSV) читать как `utf-8-sig`;
- кодировка указывается **явно** при каждом открытии текстового файла во всём
  проекте - так ни один файл не зависит от настроек окружения.
